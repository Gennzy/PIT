# ПИТ V4.3 — усиление входа и сессий

## Что изменено

- В production и Vercel cookies клиентов, владельцев и администратора автоматически получают Secure, даже при COOKIE_SECURE=false. Локальная разработка по HTTP по-прежнему возможна. HttpOnly и SameSite=Strict сохранены; удаление cookies использует тот же Secure-флаг.
- Для администратора платформы в production/Vercel обязателен второй фактор TOTP: приложение-аутентификатор, SHA1, 6 цифр, период 30 секунд. Отсутствующий или некорректный ключ MFA закрывает вход, а не отключает второй фактор. PLATFORM_MFA_REQUIRED=false НЕ отключает MFA в production.
- Использованный временной счётчик OTP фиксируется атомарно в базе. Тот же или более старый счётчик не может выдать вторую сессию. Код проверяется в окне ±30 секунд для небольшого рассогласования часов.
- Смена пароля, PLATFORM_ADMIN_SECRET или ключа MFA делает прежние сессии платформы недействительными. Ротация ключа MFA требует повторной настройки аутентификатора.
- Ограничения попыток сохраняются в PostgreSQL общей атомарной функцией consume_rate_limit из миграции 001, не в памяти экземпляра Vercel. Для тестов SQLite используется отдельный имитатор.
- Лимиты за 10 минут: платформа — 20 попыток на IP и 8 на аккаунт; обычный вход/регистрация — 60 на IP и 15 на аккаунт внутри СТО. Учитываются все попытки, включая успешные. Одинаковые email в разных СТО не блокируют друг друга по аккаунтному счётчику. IP-лимит общий для обычного входа. Ответ при превышении — 429 и Retry-After: 600. Фиксированное окно может требовать подождать до 10 минут; его нельзя сбросить перезапуском Vercel.
- Прокси-заголовок адреса принимается только в среде Vercel; при прямом подключении используется адрес сокета. Для другого reverse proxy нужна отдельная корректная конфигурация доверенных прокси. Не подменяйте это доверием к произвольному X-Forwarded-For.
- Для API добавлен no-store; в production — HSTS без includeSubDomains. Публичные статические файлы продолжают использовать свою политику обновления.
- Короткий непустой пароль и короткий PLATFORM_ADMIN_SECRET по-прежнему допускаются. Новый PLATFORM_TOTP_SECRET — другой ключ: он генерируется случайно и не предназначен для запоминания или ручного придумывания.

## Порядок внедрения — не пропускать

1. Сделать резервную копию и сначала проверить обновление на стенде Supabase/PostgreSQL. В среде разработки тесты выполнялись на SQLite; production-миграция не применялась автоматически.
2. После установленных миграций 001–004 выполнить supabase/005_security.sql в SQL Editor Supabase. Она добавляет только таблицу предотвращения повторных OTP, включает RLS и закрывает браузерный доступ; клиентов, пароли, компании и заказы не перезаписывает. Таблица хранит отпечаток конфигурации, счётчик времени и дату, но не ключ MFA и не введённый код.
3. На своём доверенном компьютере, внутри обновлённого проекта, выполнить:

```bash
npm run mfa:setup -- ваш-email-администратора
```

Команда печатает НОВЫЙ случайный ключ и локальный otpauth URI. Она ничего не меняет на сервере и не создаёт пользователя. Каждый запуск генерирует другой ключ. Не используйте открытый тестовый ключ из tests/security.test.js.

4. В Google Authenticator, 2FAS, Microsoft Authenticator или совместимом приложении добавить учётную запись вручную: название ПИТ, ключ из предыдущего шага, тип «по времени» / TOTP. Включить автоматическую синхронизацию времени на телефоне.
5. Сохранить копию этого ключа в защищённом менеджере паролей. Не отправлять ключ или otpauth URI в чат, email, публичный QR-сервис, Git или скриншот. В выводе терминала содержится секрет: не сохраняйте его в CI-логах.
6. В Vercel → Environment Variables установить серверный PLATFORM_TOTP_SECRET точно в это значение. Для production также рекомендуется независимый случайный AUTH_RATE_SECRET. Прежние PLATFORM_ADMIN_EMAIL/PASSWORD/SECRET сохраняются. Не использовать префикс NEXT_PUBLIC_ для каких-либо секретов. Значения Preview и Production настраиваются отдельно.
7. Загрузить обновлённый код и выполнить Redeploy ПОСЛЕ миграции и настройки ключа. Проверить вход: email, прежний пароль и текущий код аутентификатора. Старые сессии платформы будут завершены. Проверить обычные аккаунты, отказ при неверном OTP и отсутствие прямого браузерного доступа к новой таблице. Проверьте флаги cookies через DevTools на HTTPS.

Не деплойте V4.3 в production без настройки MFA: администратор не сможет войти, пока ключ не будет добавлен и выполнен Redeploy. Пользовательские аккаунты не получают обязательную MFA в этой версии.

## Восстановление доступа

- Сначала восстановить запись аутентификатора из защищённой резервной копии того же ключа.
- Если копии нет, владелец доступа к хостингу генерирует новый ключ на доверенном устройстве, добавляет его в аутентификатор и серверное окружение Vercel, затем выполняет Redeploy. Старые сессии платформы и старые коды перестают работать. Нужно убедиться, что меняется нужное окружение.
- Публичного сброса MFA по email, временного парольного обхода и встроенных recovery-кодов нет. Защитите аккаунты Vercel и Supabase собственной MFA; ограничьте круг людей с доступом к окружению.
- Не очищайте таблицу replay вручную для «повторного использования» текущего кода; дождитесь нового кода. При неоднозначном сетевом ответе код мог уже быть использован.
- При откате на V4.2 обязательный второй фактор исчезнет. Такой откат снижает защиту: ограничьте доступ к платформе на уровне хостинга и согласуйте безопасный план восстановления.

## Проверки и границы

85/85 автоматических теста и сборка прошли: 66 прежних сценариев и 19 новых. Проверены RFC6238-векторы, Secure в production/Vercel, обязательная настройка MFA, неверные/отсутствующие/повторные коды и одновременный вход с одним кодом, вход с коротким паролем и MFA, отзыв сессии при ротации ключа, меж-IP ограничения аккаунта, раздельные счётчики СТО, окно лимитера, отсутствие ключа в публичном ответе, защита от поддельного прокси-заголовка, RLS-миграция и прежняя изоляция данных.

Это не независимый аудит, не доказательство полной защищённости и не нагрузочный тест. TOTP не является фишинг-устойчивым фактором; WebAuthn/passkeys, MFA владельцев, WAF, мониторинг подозрительных входов и полноценные recovery-коды не добавлены. Аккаунтное ограничение может временно блокировать вход при атаке — окно восстанавливается автоматически. Политику лимитов нужно проверить с реальными нагрузками и общими корпоративными IP.

Текущее состояние production, разрешения реального бакета, резервные копии и права подключения PostgreSQL необходимо проверить отдельно. Код не был автоматически отправлен в GitHub, Vercel или Supabase.
